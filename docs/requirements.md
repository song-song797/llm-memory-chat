# LLM Memory Chat — 需求分析文档

## 1. 项目概述

### 1.1 背景

传统 LLM 聊天应用的核心痛点是**无状态**：每次新建对话都从零开始，助手无法记住用户的偏好、项目背景或历史决策。这导致用户反复提供相同背景信息，体验割裂且低效。

### 1.2 项目目标

构建一个具备**跨会话永久记忆能力**的 LLM 对话系统，使助手能够：

- 跨对话记住用户的偏好和习惯。
- 按项目组织对话和记忆，隔离不同工作上下文。
- 在对话中自动识别值得记住的信息，经用户确认后持久化。
- 支持多模型接入和切换，适配不同推理需求。

### 1.3 项目定位

面向个人开发者和小型技术团队的知识型对话助手，适合需要长期维护项目上下文、技术决策记录、个人偏好管理的场景。

### 1.4 排除范围（不做什么）

以下功能明确不在本项目范围内：

| 编号 | 排除项 | 排除原因 |
|------|--------|----------|
| E-01 | 多租户 / 组织级权限管理 | 定位为个人/小团队工具，无需组织架构 |
| E-02 | 实时协作 / 多人共享对话 | 非协作场景，单人使用为主 |
| E-03 | 自托管 LLM 模型推理 | 通过外部 API 接入即可满足需求 |
| E-04 | 移动端原生应用 | 优先 Web 端，响应式布局适配移动浏览器 |
| E-05 | 语音输入 / 输出 | 当前聚焦文本交互 |
| E-06 | RAG 文档检索（非记忆类的知识库问答） | 与"记忆"场景有本质区别，属于独立产品方向 |
| E-07 | 国际化 | 当前仅支持中文界面和对话 |

## 2. 术语与定义

| 术语 | 定义 |
|------|------|
| 记忆（Memory） | 经用户确认或系统自动提取并持久化的用户相关信息，可在后续对话中注入上下文 |
| 记忆候选（Memory Candidate） | 系统从对话中提取的潜在记忆，需用户审核后方可转正 |
| 记忆文档（Memory Document） | 按 scope 聚合多条记忆生成的 Markdown 文档，用于批量注入上下文 |
| 作用域（Scope） | 记忆的生效范围，分为 global（全局）、project（项目级）、conversation（会话级）三级 |
| 推理等级（Reasoning Level） | LLM 推理深度控制，分为 off（关闭）、standard（标准）、deep（深度）三级 |
| 内联候选（Inline Candidate） | 高置信度的记忆候选，直接在聊天界面气泡旁展示 |
| 显式记忆意图 | 用户消息中包含"请记住"、"以后你要记得"等明确指令 |
| V1 端点 | 面向开发者/集成的 API 端点（/api/v1），支持可选认证和可配置记忆注入 |

## 3. 用户角色

| 角色 | 定义 | 典型场景 | 能力边界 |
|------|------|----------|----------|
| 注册用户 | 通过邮箱密码注册并登录的正式用户 | 个人开发者日常使用、项目知识管理 | 完整的对话、记忆、项目、设置能力；数据按用户隔离 |
| 匿名用户 | 未注册或未登录的临时访问者 | 快速体验聊天能力、首页导览 | 仅限基础聊天（V1 端点），无记忆注入、无项目管理、对话不持久关联 |

## 4. 用户场景

### UC-01：新用户首次体验记忆能力

> 张三是一名后端开发者，首次使用系统。注册登录后，在聊天中说"我主要用 Python 和 Go 开发，偏好函数式风格"。系统识别为记忆候选，在聊天气泡旁展示内联卡片，张三点击"记住"。后续所有对话中，助手都会考虑这一偏好给出建议。

### UC-02：按项目隔离工作上下文

> 张三同时维护两个项目"支付系统"和"推荐引擎"。他分别创建项目并关联对话。在"支付系统"项目中的技术决策记忆不会出现在"推荐引擎"项目的对话中。全局偏好（如编码风格）则在所有项目中共享。

### UC-03：通过 API 集成到自有工具

> 李四是一名 DevOps 工程师，通过 V1 API 端点将记忆能力集成到自己的自动化脚本中。使用 `/api/v1/chat/auto` 端点自动注入记忆，无需额外配置。

## 5. 功能需求

> 优先级定义：P0 = 核心必做（MVP） / P1 = 重要（首个正式版本） / P2 = 可选增强

### 5.1 用户认证（AUTH）

| 编号 | 功能 | 描述 | 优先级 |
|------|------|------|--------|
| AUTH-01 | 用户注册 | 邮箱 + 密码注册，邮箱唯一，密码最少 8 位，注册后自动登录 | P0 |
| AUTH-02 | 用户登录 | 邮箱 + 密码登录，返回 Bearer Token | P0 |
| AUTH-03 | 用户登出 | 使当前 Token 失效 | P0 |
| AUTH-04 | 获取当前用户 | 验证 Token 有效性，返回用户信息 | P0 |

### 5.2 对话管理（CONV）

| 编号 | 功能 | 描述 | 优先级 |
|------|------|------|--------|
| CONV-01 | 创建对话 | 发送第一条消息时自动创建，标题取消息前 50 字符 | P0 |
| CONV-02 | 对话列表 | 侧边栏展示，按更新时间倒序，支持搜索 | P0 |
| CONV-03 | 切换对话 | 点击侧边栏切换当前活跃对话，消息和记忆同步刷新 | P0 |
| CONV-04 | 重命名对话 | 修改对话标题 | P1 |
| CONV-05 | 置顶对话 | 对话可置顶，置顶对话排在最前 | P1 |
| CONV-06 | 删除对话 | 删除单个对话及其消息和附件 | P0 |
| CONV-07 | 清空全部对话 | 一键清除当前用户的所有对话，需二次确认 | P1 |
| CONV-08 | 消息重新生成 | 对助手回复点击重新生成，生成新版本 | P1 |
| CONV-09 | 消息版本切换 | 查看助手回复的历史版本，可切换回任一版本 | P1 |

### 5.3 聊天核心（CHAT）

| 编号 | 功能 | 描述 | 优先级 |
|------|------|------|--------|
| CHAT-01 | 流式对话 | SSE 流式返回助手回答，逐 token 渲染 | P0 |
| CHAT-02 | 多模型切换 | 支持多个 LLM 模型，可在聊天界面随时切换 | P0 |
| CHAT-03 | 推理等级控制 | 支持 off / standard / deep 三级推理强度，不同模型有不同推理模式 | P1 |
| CHAT-04 | 附件上传 | 支持上传图片（base64 注入上下文）和普通文件（元信息注入），每条消息最多 6 个附件，单文件不超过 10 MB | P1 |
| CHAT-05 | 上下文窗口 | 保留最近 N 条消息作为短期上下文（默认 20 条，可配置） | P0 |
| CHAT-06 | 首页导览 Agent | 未登录首页有导览 Agent，介绍网站能力，最多保留 8 轮历史 | P2 |

### 5.4 长期记忆系统（MEM）

| 编号 | 功能 | 描述 | 优先级 |
|------|------|------|--------|
| MEM-01 | 显式记忆识别 | 用户消息包含"请记住"、"以后你要记得"等关键词时触发 | P0 |
| MEM-02 | 自动记忆抽取 | 每轮对话后，后台异步调用 LLM 判断是否值得生成记忆候选 | P1 |
| MEM-03 | 候选展示 | 候选以 inline（聊天气泡旁）或 settings（设置面板）两种方式呈现 | P1 |
| MEM-04 | 候选审核操作 | 用户可接受、拒绝、或延后处理记忆候选 | P1 |
| MEM-05 | 记忆作用域 | 支持 global（跨项目）/ project（项目内）/ conversation（会话内）三级作用域 | P0 |
| MEM-06 | 记忆 CRUD | 手动创建、编辑内容、启用/停用、删除记忆 | P0 |
| MEM-07 | 记忆自动注入 | 聊天时自动将相关记忆注入上下文，作用域匹配时生效 | P0 |
| MEM-08 | 会话记忆压缩 | 会话级记忆超过阈值（条数或字符数）时，自动调用 LLM 压缩为摘要 | P1 |
| MEM-09 | 记忆文档 | 按 scope 聚合生成 Markdown 文档，优先使用文档注入，缺少时降级为逐条注入 | P1 |
| MEM-10 | 记忆历史版本 | 记忆变更保留完整版本链，记录变更原因和操作类型 | P2 |
| MEM-11 | 记忆审计日志 | 记忆的所有操作留有审计记录，包含变更前后状态快照 | P2 |
| MEM-12 | 向量语义检索 | 可选，使用 embedding + pgvector 进行语义相似度搜索，替代时间排序 | P2 |

## 6. 业务规则

| 编号 | 规则 | 说明 | 备注 |
|------|------|------|------|
| BR-01 | 记忆注入优先级 | 当记忆文档存在且 is_stale=false 时，使用文档内容注入；否则降级为逐条记忆注入 | — |
| BR-02 | 作用域冲突优先级 | 当同一信息在不同作用域存在冲突记忆时，conversation > project > global | 粒度越细优先级越高 |
| BR-03 | 候选展示位置决定 | confidence >= 85（可调）且 importance >= 80（可调）时 inline 展示，否则放入 settings 面板 | 阈值通过 MEMORY_INLINE_CONFIDENCE_THRESHOLD 和 MEMORY_INLINE_IMPORTANCE_THRESHOLD 配置 |
| BR-04 | 会话记忆自动接受 | 当 scope=conversation 且 MEMORY_CONVERSATION_AUTO_ACCEPT=true 时，候选自动转正，无需用户审核 | — |
| BR-05 | 敏感信息过滤 | LLM 抽取候选时，如识别为敏感信息（密码、身份证等），标记 sensitive=true 并跳过 | — |
| BR-06 | 记忆去重 | 精确匹配（normalize 后 kind:content 相同）标记为 duplicate；身份匹配（preference 类按主题关键词比对）标记为 update | — |
| BR-07 | 跨模型上下文 | 助手回复的历史消息如果来自不同模型，以 system 角色注入并标注来源模型，避免身份混淆 | — |
| BR-08 | 匿名用户限制 | 匿名用户通过 V1 端点聊天时，不注入记忆、不创建记忆候选、不关联项目 | — |

## 7. 数据需求

### 7.1 数据实体

系统管理以下核心数据实体：

| 实体 | 估算量级 | 数据特征 | 敏感程度 |
|------|----------|----------|----------|
| User | 百级 | 邮箱唯一，密码 bcrypt 哈希 | 高（含认证信息） |
| Project | 用户 × 十级 | 软删除（archived_at），按用户隔离 | 低 |
| Conversation | 用户 × 百级 | 关联项目和用户，按更新时间排序 | 中（含对话内容） |
| Message | 用户 × 千级 | 版本链（parent_message_id），附件关联 | 中（含对话内容） |
| Memory | 用户 × 百级 | 三级作用域，启用/停用控制，支持归档 | 中（含用户信息） |
| MemoryCandidate | 用户 × 百级 | 临时状态（pending → accepted/dismissed） | 中 |
| MemoryDocument | 用户 × 十级 | 按 scope 聚合，Markdown 格式 | 中 |
| Attachment | 用户 × 百级 | 文件存储在本地 uploads 目录 | 视内容而定 |

### 7.2 数据隔离

- 所有业务数据按 user_id 隔离，API 层强制校验数据归属。
- 匿名用户的对话 user_id 为 null，无记忆和项目关联。

### 7.3 数据保留与删除策略

| 数据类型 | 删除方式 | 说明 |
|----------|----------|------|
| 对话及关联消息/附件 | 硬删除 | 级联删除（ON DELETE CASCADE），不可恢复 |
| 记忆 | 硬删除 | 直接删除记录 |
| 记忆归档 | 软删除 | 设置 archived_at 和 status=archived，数据保留 |
| 项目归档 | 软删除 | 设置 archived_at，数据保留 |
| 用户账号 | 不支持删除 | 当前版本不提供账号注销功能 |

## 9. 非功能需求

### 9.1 性能

| 编号 | 指标 | 目标值 | 测量方式 |
|------|------|--------|----------|
| NFR-P01 | 首字节延迟（系统额外开销） | <= 100ms | 从收到请求到发起 LLM API 调用 |
| NFR-P02 | 记忆注入耗时 | <= 50ms | 含查询数据库 + 构建上下文 |
| NFR-P03 | 前端首屏加载 | <= 3s | Lighthouse Performance Score >= 80 |
| NFR-P04 | SSE chunk 间隔 | 取决于上游 LLM | 系统本身不引入额外 buffering |

### 9.2 可靠性

| 编号 | 要求 | 实现策略 |
|------|------|----------|
| NFR-R01 | 记忆降级 | 记忆操作失败时，聊天功能不受影响，降级为无记忆模式 |
| NFR-R02 | 数据库容错 | 数据库连接异常时，返回 HTTP 503 并在日志中记录原因 |
| NFR-R03 | 流式中断恢复 | 用户关闭页面导致流式传输中断时，后端正常保存已生成的部分回复 |

### 9.3 安全

| 编号 | 要求 | 实现方式 |
|------|------|----------|
| NFR-S01 | 密码存储 | bcrypt 哈希，不可逆 |
| NFR-S02 | 会话管理 | Token SHA256 哈希存储，支持单 Token 粒度主动失效 |
| NFR-S03 | 数据隔离 | 所有数据查询强制 WHERE user_id = ?，更新/删除操作先校验归属 |
| NFR-S04 | 敏感信息过滤 | LLM 抽取记忆时自动识别并跳过含敏感信息的候选 |
| NFR-S05 | CORS | 开发环境 allow_origins=["*"]，生产环境应限制为前端域名 |
| NFR-S06 | 附件安全 | 单文件 10 MB 上限，每条消息最多 6 个附件，存储使用随机文件名 |

### 9.4 兼容性

| 维度 | 范围 |
|------|------|
| 数据库 | SQLite（开发默认）/ PostgreSQL（生产推荐，向量检索必需） |
| LLM 服务 | 任何兼容 OpenAI Chat Completions API 的服务 |
| 浏览器 | Chrome、Firefox、Safari、Edge 最近两个主版本 |
| 运行环境 | Python >= 3.12，Node.js >= 18 |

### 9.5 可维护性

| 编号 | 要求 | 说明 |
|------|------|------|
| NFR-M01 | 数据库迁移管理 | 使用 Alembic 版本管理，每次变更必须有对应的迁移脚本 |
| NFR-M02 | 模型可扩展 | 模型目录通过 config.py 配置，新增模型只需修改配置 |
| NFR-M03 | 配置外部化 | 所有配置项通过环境变量注入，支持 .env 文件 |

## 10. 验收标准

### 10.1 认证（AUTH）

| 需求编号 | 验收条件 |
|----------|----------|
| AUTH-01 | 使用合法邮箱和 >= 8 位密码可注册成功；重复邮箱返回 409；密码不足 8 位返回 400 |
| AUTH-02 | 正确凭据登录返回 token；错误凭据返回 401 |
| AUTH-03 | 登出后 token 失效，再次调用 /me 返回 401 |
| AUTH-04 | 有效 token 返回用户信息；无效/过期 token 返回 401 |

### 10.2 对话管理（CONV）

| 需求编号 | 验收条件 |
|----------|----------|
| CONV-01 | 新对话首次发消息后自动出现在对话列表，标题为消息前 50 字符 |
| CONV-02 | 对话列表按更新时间倒序，支持关键字搜索 |
| CONV-03 | 切换对话后，消息列表和记忆状态正确刷新 |
| CONV-04 | 修改标题后，侧边栏和对话详情中标题同步更新 |
| CONV-05 | 置顶对话始终排在列表最前；取消置顶后恢复按时间排序 |
| CONV-06 | 删除对话后，该对话的消息和附件不可再访问 |
| CONV-07 | 清空全部对话后，对话列表为空，需二次确认弹窗 |
| CONV-08 | 重新生成后可查看多个版本，新版本内容不同于前一版本 |
| CONV-09 | 切换到历史版本后，聊天界面展示对应版本内容，该版本标记为 current |

### 10.3 聊天核心（CHAT）

| 需求编号 | 验收条件 |
|----------|----------|
| CHAT-01 | 发送消息后，助手回答逐字流式渲染，无全量等待；中断后已生成部分正常保存 |
| CHAT-02 | 切换模型后下次对话使用新模型，上下文中历史消息标注来源模型 |
| CHAT-03 | 设置推理等级后，LLM 调用参数正确映射（参见设计文档 §5 推理模式映射表） |
| CHAT-04 | 上传图片后图片内容被注入上下文；上传文件后文件名和元信息被注入；超过 6 个附件返回 400；超过 10 MB 返回 400 |
| CHAT-05 | 上下文窗口保留最近 N 条消息，超出部分不发送给 LLM |
| CHAT-06 | 未登录首页可发起导览对话，最多 8 轮；登录后导览对话不保留 |

### 10.4 记忆系统（MEM）

| 需求编号 | 验收条件 |
|----------|----------|
| MEM-01 | 消息包含"请记住"后，系统创建记忆候选（或自动接受），后续对话中可查到该记忆 |
| MEM-02 | 普通对话后，后台异步生成记忆候选（如有价值），候选出现在 inline 或 settings 面板 |
| MEM-03 | 高置信度候选（confidence >= 阈值）出现在聊天气泡旁；低置信度候选出现在设置面板 |
| MEM-04 | 接受候选后生成正式记忆；拒绝后候选消失；延后后候选移至设置面板 |
| MEM-05 | 记忆按 global / project / conversation 作用域隔离，不同作用域的记忆不互相注入 |
| MEM-06 | 手动创建的记忆立即可在列表中查看；编辑后内容更新；停用后不再注入 |
| MEM-07 | 已启用的记忆在后续对话中被注入上下文（可在 LLM 调用的 messages 中验证） |
| MEM-08 | 会话记忆超过阈值后自动触发压缩，原记忆归档，生成压缩摘要记忆 |
| MEM-09 | 记忆文档按 scope 聚合生成；文档存在且非 stale 时优先使用文档注入 |
| MEM-10 | 记忆编辑后历史版本保留，可查看变更链 |
| MEM-11 | 记忆的创建、更新、删除、归档操作均产生审计日志 |
| MEM-12 | PostgreSQL + pgvector 环境下，记忆按语义相似度排序；SQLite 环境下按时间排序 |

### 10.5 项目工作区（PROJ）

| 需求编号 | 验收条件 |
|----------|----------|
| PROJ-01 | 创建项目后可设置名称、描述、默认模型、默认推理等级 |
| PROJ-02 | 项目下的对话不出现在项目外；项目记忆只在该项目对话中注入 |
| PROJ-03 | 项目级记忆在该项目所有对话中注入，不影响其他项目 |
| PROJ-04 | 修改项目设置后，新建对话使用新设置 |
| PROJ-05 | 归档项目后，项目对话从侧边栏消失，但通过 API 仍可查询历史数据 |

### 10.6 API 调试器（API）

| 需求编号 | 验收条件 |
|----------|----------|
| API-01 | 可配置端点、模型、推理等级、stream 模式、记忆参数 |
| API-02 | 发送请求后正确展示 SSE 流式结果或 JSON 结果 |
| API-03 | 可一键生成 Python / JavaScript 调用代码片段 |
| API-04 | 调试历史包含 token 用量、耗时、状态码，可查看历史记录 |
| API-05 | 各端点有对应的使用说明文档 |

### 10.7 系统设置（SET）

| 需求编号 | 验收条件 |
|----------|----------|
| SET-01 | 可在五种主题间切换，切换后立即生效，刷新后保持 |
| SET-02 | 侧边栏可折叠/展开，状态刷新后保持 |
| SET-03 | 清空所有对话数据后，对话列表和消息均为空，需二次确认 |

## 11. 约束与假设

| 编号 | 约束/假设 | 说明 |
|------|-----------|------|
| C-01 | 单机部署 | 系统以单机部署为主，暂不考虑分布式和高可用架构 |
| C-02 | 外部 LLM 依赖 | LLM 通过外部 API 调用，需要配置有效的 API Key；网络异常时聊天不可用 |
| C-03 | 记忆抽取不确定性 | 记忆自动抽取依赖 LLM 推理，存在误判可能，因此采用候选审核机制（conversation scope 除外） |
| C-04 | 向量检索依赖 | 向量检索功能依赖 PostgreSQL + pgvector 扩展，SQLite 环境下自动降级为时间排序 |
| C-05 | 开发环境配置 | 前端通过 Vite 代理访问后端，开发环境前后端分离部署；生产环境建议反向代理合并 |
| C-06 | 中文限定 | 当前版本仅支持中文界面和中文对话，暂不规划国际化 |
